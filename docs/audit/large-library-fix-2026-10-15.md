# 大资料库容量错误修复（2026-10-15）

用户提供的 `qkd` 场景指向 `bi_sai/tiaozhanbei`，错误为
`library total size exceeds 134217728 bytes`。旧实现按整库累计 128 MiB 硬失败，
并保存所有源文件原始字节。实际文件夹包含大量临时文件、历史副本和原始实验结果，
因此小型示例的测试结果没有覆盖这个真实使用规模。

## 修复行为

- 扫描只保留元数据与流式 SHA256；解析逐文件按需读取，并校验扫描后的内容变化。
- 默认跳过嵌套 `tmp`/`temp`，保留 `output`、`results`、`data` 等可能有答辩依据的目录。
- 按格式与内容哈希去重，报告规范来源；不同格式不会因相同字节错误合并。
- 文档、代码、PDF 先于批量 JSON/CSV；单文件上限 32 MiB、独立内容预算 2 GiB、
  片段上限 50,000。字节/片段超限按整份文件跳过，继续处理其余文件，不保留半份文件。
- 部分覆盖明确显示受限/跳过/重复数量，“索引详情”可查看完整只读报告；
  空结果也保留诊断，失败刷新保留之前的可用索引。
- 向量存为压缩二进制，元数据原子替换；分批 64 片段显示进度，缓存 schema 升至 4。
- 紧凑关键词表示保留原评分，避免全库提前展开中文二元/三元词项集合。
- 科研 PDF 改用 PyMuPDF，保留真实 PDF 页序、加密与空白诊断；缺包时才回退 pypdf。

## 当前验证

- 完整 Classbot 测试：**387 passed，1 skipped**，34.96 秒。
- 跳过测试需要 Windows 创建符号链接权限；没有修改系统权限。
- Ruff 与 `git diff --check` 通过。
- 50,000 × 384 个 float32 向量（二进制原始约 76.8 MB）写入并读回相同，
  压缩缓存约 71.1 MB，未触发旧 JSON 缓存膨胀问题。
- 100 个各 1,000 字中文片段的紧凑词项构建新增峰值约 4 KiB，
  兼容性测试覆盖中文、单字边界、标识符、camelCase、snake_case 和数字。
- 真实目录扫描及解析完成：2,194 个独立候选文件、409,367,378 字节，
  扫描快照保留的原始内容为 0 字节。解析约 57.53 秒。
- 解析阶段纳入 1,341 个文件、50,000 片段，包括 Python 457、Markdown 254、
  PDF 68、PPTX 3、DOCX 1；802 个精确副本被去重，840 个文件达到处理边界。
  总跳过计数还包括隐藏、依赖、临时目录、不支持格式和解析失败。

真实大库的完整向量计算未完成，耗时较长的验证进程已停止；没有留下后台计算。
扫描/解析通过不等于实际大库向量索引已就绪。更新后的应用需要重启，再刷新资料索引；
首次计算会显示片段进度。用户资料未修改，没有把真实资料发送给 DeepSeek。
